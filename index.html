Runbook · the actual plan for your move

Phase 1 · Build the targetT minus 7 days

Nothing touches production in this phase.
  • Ubuntu LTS, Nginx, PHP-FPM 8.3 with bcmath, intl, soap, sockets, xsl, zip, gd, opcache
  • MySQL 8, Redis 7, OpenSearch 2.x, Node LTS, Composer 2
  • Redis split into three databases for default cache, page cache and sessions
  • OpenSearch heap at half the memory, capped at 31 GB
  • Nginx from the Magento sample config, TLS issued and stapled
    certbot certonly --nginx -d your-domain
  • Same layout available as a Docker Compose stack if you prefer containers

Phase 2 · First copy and live replicationT minus 3 days

The new server starts following the old one.
  • Consistent dump that also records the binlog position
    mysqldump --single-transaction --source-data=2 --routines --triggers
  • Restore on the target, then point it at the source and start following
    CHANGE REPLICATION SOURCE TO ... ; START REPLICA;
  • Media and import folders copied, then re-copied as deltas
    rsync -a --delete pub/media var/importexport
  • Code deployed from your repo, then compiled for three locales
    setup:di:compile & setup:static-content:deploy de_DE en_US it_IT
  • Extension licences re-registered for Webkul, Landofcoder and WeltPixel
  • The encryption key is carried across with the config, otherwise every saved Stripe token and encrypted setting becomes unreadable on the new server
    app/etc/env.php: crypt.key
  • Media storage setting checked first, because if media lives in the database a file copy moves nothing
    core_config_data: system/media_storage_configuration

Phase 3 · Validate while production runsT minus 2 days

Tested under the real domain without moving any traffic.
  • Local hosts override so the target answers on the production hostname
  • Full reindex and cache warm
    bin/magento indexer:reindex & cache:flush
  • Stripe in test mode, one charge plus a replayed webhook with signature check
  • Webkul seller login, product upload and a complete order
  • Node API health and one gate open request against test keys
  • Replication confirmed level
    SHOW REPLICA STATUS: Seconds_Behind_Source = 0

Phase 4 · Cutoverunder 60 seconds

The only moment customers could feel anything.
  • A day earlier the DNS record drops to a 60 second time to live
  • Only the host records change. MX, SPF, DKIM and DMARC are copied first, so email keeps flowing while the servers move
  • Source set to read only, so no order can be lost mid flight
    bin/magento maintenance:enable
  • Wait for zero replication lag, then one final media delta
  • Target promoted and opened for writes
    STOP REPLICA; SET GLOBAL read_only = OFF;
  • Reverse proxy upstream switched to the target, DNS follows
  • Stripe webhook endpoints repointed and signature verified
  • Read only released, checkout smoke test, New Relic watched live

Phase 5 · Watch window and rollback48 hours

The bridge stays standing until you are sure.
  • Replication reversed, target to source, so the old server stays current
  • Rollback triggers agreed in advance: checkout failures, gate API errors, error rate above the agreed line, or broken replication
  • Rollback is a proxy and DNS change back to the source, under 30 seconds, with no data left behind
  • Nightly backups and a restore rehearsal before the window closes

What we need from yousoftware only

Nothing physical, nothing from production customers.
  • Repository or branch access for the Magento and Node applications
  • Shell or panel access on the current servers, and DNS zone editing
  • Dump or read replica permission on the database
  • Stripe test keys and the current webhook endpoint list
  • Licence keys for Webkul, Landofcoder and WeltPixel
  • A New Relic invite so monitoring continues without a gap

Proven approach · a similar migration

The cutover took 45 seconds. Getting there took nine days.

A multi-vendor Magento 2.4 marketplace, managed hosting to a self managed box. replace with your team's real project
  • That ratio is the method, not an estimate. Nine days of building, replicating and validating are exactly why the visible part lasted under a minute.
  • The find that saved the project. Media looked like a simple folder copy until the database said otherwise, media storage was set to database, so a file copy would have carried nothing and the storefront would have opened with every product image missing. Most teams learn this after the cutover.
  • What actually took longest. Not the database. Compiling and deploying static content for every locale, then warming caches, ate more hours than the data move.
  • Result. Zero records lost, no rollback needed, and the old server stayed in sync for two days in case it was.
